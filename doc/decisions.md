# 技術判断の記録

このサイトを作り直したときに下した判断と、その理由をまとめたものです。同じ議論を繰り返さないために残しています。

## インフラ

### GitHub Pages に移行し、Firebase を全廃した

Firebase が担っていたのは Hosting・Authentication・Analytics の 3 つでした。認証をやめ、アクセス解析もやめた結果、残るのは静的配信だけになり、Firebase を使う理由がなくなりました。

GitHub Pages は無料プランでは public リポジトリからしか配信できません。掲載内容をすべて公開前提としたため、public 化の障壁はなくなりました。

### Hono を採用しなかった

当初は Hono の導入を検討しましたが、認証もサーバーサイド処理も無くなったため、置いても素通りするだけの API になります。技術的な理由がないので見送りました。

Hono を使うなら Cloudflare Workers などの実行環境が別途必要になり、管理対象が 1 つ増えます。GitHub Pages は純粋な静的ホスティングなので、そもそも置き場所がありません。

### cc-sdd（仕様駆動開発）を導入しなかった

個人 1 人・半年に 1 回更新の規模に対して、requirements → design → tasks の 3 段階ワークフローはオーバースペックです。`doc/` の 3 ファイルで足ります。

### 公開 URL はプロジェクトページにした

`https://f18c052f.github.io/my-profile-site/` で配信します。既存リポジトリと履歴をそのまま活かせるためです。

独自ドメインに移行する場合は、`vite.config.ts` の `base` を `'/'` に戻し、`public/CNAME` を追加してください。

### `base` を環境で分岐させない

`base: '/my-profile-site/'` は dev でも prod でも同じです。`NODE_ENV` で分岐させると、base 起因の不具合をローカルで一切再現できなくなり、「ローカルでは動いたが本番で壊れる」典型パターンになります。

その代わり、**ローカルの開発サーバーも `/my-profile-site/` で開く必要があります**（`/` は 404）。

CI の Playwright は `vite dev` ではなく `vite preview` に対して実行します。実際のビルド成果物を base 付きで配信するため、サブパス周りの破綻を CI が捕まえられます。

## セキュリティ

### パスワード認証を削除した

旧実装は Firebase Auth でパスワードを検証していましたが、**保護対象である職務経歴の詳細は i18n ファイルに静的に埋め込まれており、認証前からデプロイ済みの JS バンドルに平文で含まれていました**（ビルド成果物内に実社名がそのまま存在することを確認）。つまり認証は視覚的なゲートにすぎず、機密性をまったく提供していませんでした。

静的サイトである以上これを正しく直す方法はないため、掲載内容を公開可能な情報に限ることで要件自体を解消しました。

## パフォーマンス

### 画像はビルド時プラグインではなく事前変換にした

`vite-plugin-image-optimizer` などを使うと、CI の毎ビルドで数十 MB を再エンコードすることになります。写真は年に数回しか変わらないので割に合いません。

`pnpm images:build` で手動生成し、生成物をコミットします。一度目視で品質を確認すれば、以後は決定的です。

生成物は `public/` ではなく `src/` 配下に置いて ESM import します。理由は 3 つあります。

1. Vite のコンテンツハッシュ付きファイル名になり、長期キャッシュが効く
2. `base` が自動で付与されるので `/my-profile-site/` を意識しなくてよい
3. 参照が切れたらビルドエラーになる

### 元画像を `assets-src/` に残した

git 履歴に既に 22MB 分が入っているため、working tree から消しても `.git` は 1 バイトも縮みません。消すメリットがない一方、サイズや品質設定を変えて再生成したくなったときに必要になります。`src/` の外なので Vite は一切触りません。

### AVIF を採用しなかった

`<picture>` + `<source>` の入れ子が必要になりライトボックスとの組み合わせが複雑化する一方、WebP 比の削減は 20〜30% 程度です。WebP はブラウザ対応が十分で `<img srcset>` 1 本で完結します。

### devicon のアイコンフォントをやめた

CDN から読むと `devicon.ttf` 1.46MB + `devicon.min.css` 127KB がかかり、**サイト内の全画像を合わせたより大きい単一アセット**でした。実際に使っているのは 23 個だけです。

`pnpm icons:build` で必要な SVG だけを devicon パッケージから取り込みます（合計 47KB）。外部 CDN への依存もなくなりました。

### 日本語 Web フォントを読み込まない

Noto Sans JP は、サブセット分割しても数百 KB かかります。画像を削った分をフォントで打ち消すのは本末転倒です。macOS の Hiragino Sans、Windows の Meiryo / BIZ UDPGothic はいずれも十分に読みやすく、端末にインストール済みならフォントスタック経由で使われます。

Inter は `@fontsource-variable/inter` で self-host します（latin サブセットのみ、47KB）。rsms.me からの読み込みはレンダリングをブロックする第三者依存でした。

## 実装

### 配色を CSS 変数 + Tailwind のセマンティック名にした

値をスペース区切りの RGB で持ち、`rgb(var(--color-x) / <alpha-value>)` として参照します。この形にしないと Tailwind の `<alpha-value>` プレースホルダが機能せず、`bg-surface/80`（ヘッダーの半透明）のような書き方ができません。

結果としてコンポーネントから `dark:` 接頭辞が消え、配色の切り替えが 1 箇所で済みます。

**例外が 1 つあります。** スキルのアイコンにはダークモードでのみ明るい下地を敷いています（`carbon-original` が `#000000`、`wordpress-plain` が `#494949` で暗い背景に沈むため）。これは配色トークンではなく可読性のための処置なので `dark:` を直接使っています。

### `revealProps` をコンポーネントではなく props オブジェクトにした

`<Reveal>` のようなラッパーにすると DOM が 1 段深くなり、`className` の受け渡しや `transition` の上書きを全部 props で受け直すことになります。plain object なら `<motion.div {...revealProps}>` の 1 行で既存の呼び出しを置換できます。

### ライトボックスを自前実装にした

`yet-another-react-lightbox` などを入れなかった理由は 3 つです。

1. framer-motion が既に依存にあるので、アニメーションの追加コストがゼロ
2. 要件が軽い（9 枚、拡大、前後移動、閉じる、キャプション）。ライブラリの機能の大半が不要
3. **ネイティブの `<dialog>` の `showModal()` が a11y の難所を全部片付ける** — フォーカストラップ、Esc、背景の不活性化、閉じたときに起動元へフォーカスを戻す処理。自前実装で最も間違えやすい部分がブラウザ実装として手に入るため、ライブラリを入れる主な動機が消えます

暗幕は `::backdrop` と `<dialog>` 自身の両方に持たせています。`::backdrop` だけに頼ると実装差やスクリーンショットで欠けることがあるためです。

### i18next の型定義を入れた

`src/i18n/i18next.d.ts` の module augmentation により、`t('...', { returnObjects: true })` が実際の配列型を返し、存在しない翻訳キーがコンパイルエラーになります。これで `as any` が 9 箇所消えました。

`en.ts` には `satisfies typeof ja` を付けているため、**日本語と英語のキー構造のずれが型エラーとして検出されます**。

**落とし穴:** 導入時に `Header.tsx` で TS2589（型の実体化が深すぎる）が出ました。原因は locale の `hobbies.items` にあった `apps: []` が `never[]` と推論され、i18next のキー型生成が組み合わせ爆発を起こしていたことです。空配列には必ず型を与えてください（`src/i18n/types.ts` を参照）。

### スキルのカテゴリ名とアイコン名を型で縛った

- カテゴリ名は `keyof typeof ja.profile.skills.categories`
- アイコン名は生成された `SkillIconName`

どちらも以前は文字列一致に依存しており、片方だけ変えると無言で壊れる状態でした。

### 資格を i18n 側、スキルを data 側に分けたままにした

一見ちぐはぐですが、**資格名は翻訳対象（「TOEIC 845点」↔「TOEIC 845」）であるのに対し、スキル名は翻訳不要な固有名詞**という性質の違いに基づいています。無理に統合していません。

### 型チェックに `tsc -b` を使わない

`tsconfig.app.json` / `tsconfig.node.json` に `composite: true` がないため、プロジェクト参照ビルドは TS6306 で失敗します。`composite` を足すと宣言ファイル出力の制約が `noEmit` と衝突して面倒なので、`tsc -p` を 2 回叩いています。

### React 18 では `fetchPriority` を小文字で渡す

React 18 は camelCase の `fetchPriority` を認識せず DOM 警告を出します。React 19 に上げたらプロパティとして渡せます（`src/components/ui/ResponsiveImage.tsx`）。
